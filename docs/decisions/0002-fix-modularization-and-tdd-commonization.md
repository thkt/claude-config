# ADR 0002: /fix モジュール化とTDD共通化

## 実装進捗

- [x] フェーズ 2:/fix のモジュール化（6 モジュール）- 完了
- [x] フェーズ 3:/code の参照更新（機能維持）- 完了
- [x] フェーズ 4: テストと検証（動作確認）- 完了
- [x] フェーズ 5: ADR 作成とドキュメント更新 - 進行中

## Context and Problem Statement

### 問題1: /fix コマンドの複雑さ

`/fix` コマンド (`~/.claude/commands/fix.md`) は 239 行で 10 以上の責任を持ち、ミラーの法則 (7±2) に違反:

| #   | 責任                                         | 行数 |
| --- | -------------------------------------------- | ---- |
| 1   | 動的コンテキスト                             | ~15  |
| 2   | 根本原因分析 (フェーズ1)                     | ~30  |
| 3   | リグレッションテストファースト (フェーズ1.5) | ~45  |
| 4   | 実装 (フェーズ2)                             | ~35  |
| 5   | 検証 (フェーズ3)                             | ~40  |
| 6   | テスト生成 (フェーズ3.5)                     | ~30  |
| 7   | 完了定義                                     | ~20  |
| 8   | 出力フォーマット                             | ~10  |
| 9   | エスカレーション                             | ~10  |
| 10  | 適用される原則                               | ~4   |

### 問題2: DRY違反（TDD知識の重複）

TDD 基礎がコマンド間で重複:

| 要素             | `/code/rgrc-cycle.md` | `/fix` フェーズ1.5/3.5 | 重複率 |
| ---------------- | --------------------- | ---------------------- | ------ |
| RGRCサイクル     | 198行                 | 暗黙的                 | ~90%   |
| ベイビーステップ | 詳細                  | 暗示                   | ~60%   |
| generator-test   | パターン1             | パターン2              | ~70%   |

### 課題

- **ミラーの法則違反**: 10 の責任 > 7±2 の認知限界
- **DRY違反**: TDD 知識が重複
- **保守性**: 変更には複数箇所の更新が必要
- **発見可能性**: TDD ガイダンスを見つけにくい
- **一貫性**: コマンド間で乖離するリスク

## Decision Drivers

1. **ミラーの法則 (7±2)** - 認知負荷を軽減
2. **DRY原則** - TDD 知識の単一真実源
3. **保守性** - 更新と拡張が容易
4. **再利用性** - コマンド間で TDD 基礎を共有
5. **ユーザー体験** - `/code` と `/fix` の機能を維持
6. **一貫性** - ADR 0001 のパターンに従う

## Considered Options

### オプションA: 現状維持（何もしない）

**利点**:

- 実装コストなし
- 破壊的変更のリスクなし
- 学習曲線なし

**欠点**:

- ミラーの法則違反が継続
- DRY 違反が持続
- 保守負担が増大
- 不整合リスクが増加

### オプションB: 完全統合

`/code` と `/fix` の TDD ロジックを単一の統合モジュールにマージ。

**利点**:

- 最大限の DRY 準拠
- 単一真実源
- 一元化された保守

**欠点**:

- コンテキスト混乱（機能 vs バグ）
- 条件ロジックの複雑さ
- 読みやすいコード違反
- 理解困難

### オプションC: ハイブリッドモジュール化（選択）

**3層アーキテクチャ**:

```text
レイヤー1: スキル（教育）
  └─ skills/tdd-fundamentals/
     ├── SKILL.md（原則）
     └── examples/（パターン）

レイヤー2: 共有（実装）
  └─ references/commands/shared/
     ├── tdd-cycle.md（RGRC詳細）
     └── test-generation.md（パターン）

レイヤー3: コマンド（実行）
  ├─ commands/fix.md + fix/（6モジュール）
  └─ references/commands/code/（参照更新）
```

**利点**:

- ✅ 原則は DRY、適用はコンテキスト固有
- ✅ ミラーの法則準拠（6 モジュール < 7±2）
- ✅ 読みやすいコードを維持（明確な分離）
- ✅ ADR 0001 パターンに従う（一貫性）
- ✅ コマンド間で再利用可能
- ✅ ユーザー体験は変更なし

**欠点**:

- 実装コスト（5 フェーズ）
- ナビゲートするファイルが増加
- 参照管理が必要

## Decision Outcome

**選択されたオプション**: オプション C（ハイブリッドモジュール化）

### 根拠

1. **DRY + 読みやすさのバランス**
   - 共通原則 → 共有
   - コンテキスト固有のロジック → 分離
   - 両方の良いところを取る

2. **ミラーの法則準拠**
   - `/fix`: 10 の責任 → 6 モジュール（7±2 以内）
   - 各モジュール: 150〜270 行（読みやすいサイズ）

3. **ADR 0001との一貫性**
   - `/code` モジュール化と同じパターン
   - 実証済みのアプローチ
   - 馴染みのある構造

4. **将来対応**
   - 新しいコマンドの追加が容易
   - TDD 基礎が再利用可能
   - 拡張可能なアーキテクチャ

### 実装戦略

#### フェーズ1: TDD基礎の共通化

**5ファイル**を作成:

```text
skills/tdd-fundamentals/
├── SKILL.md（285行）
├── examples/
│   ├── feature-driven.md（75行）
│   └── bug-driven.md（80行）

references/commands/shared/
├── tdd-cycle.md（253行）
└── test-generation.md（228行）
```

**抽出されたコンテンツ**:

- TDD 哲学（t_wada、Kent Beck）
- ベイビーステップの原則とリズム
- RGRC サイクルの実装
- generator-test パターン

#### フェーズ2: /fix のモジュール化

**7ファイル**を作成（1 メイン + 6 モジュール）:

```text
commands/
├── fix.md（164行）← 薄いラッパー
└── fix/
    ├── root-cause-analysis.md（153行）
    ├── regression-test.md（204行）
    ├── implementation.md（225行）
    ├── verification.md（248行）
    ├── test-generation.md（224行）
    └── completion.md（264行）
```

**ビフォー vs アフター**:

- 行数: 239 → 164（メインファイル、31%削減）
- 責任: 10 → 6 モジュール
- ミラーの法則: ❌ 違反 → ✅ 準拠

#### フェーズ3: /code の参照更新

**2ファイル**を更新（非破壊的）:

```text
references/commands/code/
├── rgrc-cycle.md（+ TDD基礎リファレンス）
└── test-preparation.md（+ テスト生成リファレンス）
```

**重要な原則**: 参照のみ追加、ロジック変更なし。

**結果**: `/code` 機能 100%維持。

#### フェーズ4: テストと検証

**検証結果**:

- ✅ すべてのファイル作成（13 ファイル）
- ✅ 参照が有効（30 のクロスリファレンス）
- ✅ 構造が正確（3 層アーキテクチャ）
- ✅ `/code` 機能が維持

## Consequences

### ポジティブ

**即時**:

- ✅ ミラーの法則準拠
- ✅ DRY 原則適用
- ✅ 保守性向上
- ✅ 再利用性実現

**長期**:

- ✅ 新しいコマンドの追加が容易（例: `/hotfix` モジュール化）
- ✅ TDD ガイダンスが一元化され発見可能
- ✅ コードベース全体で一貫性
- ✅ ユーザーのためのナレッジベース

### ネガティブ

**即時**:

- ⚠️ ナビゲートするファイルが増加（13 の新ファイル）
- ⚠️ 新しい構造の学習曲線
- ⚠️ 参照管理のオーバーヘッド

**長期**:

- ⚠️ 循環参照のリスク（軽減策: 慎重な設計）
- ⚠️ EN/JA 同期の維持が必要（既存の課題）

### リスクと軽減策

| リスク             | 可能性 | 影響 | 軽減策                                   |
| ------------------ | ------ | ---- | ---------------------------------------- |
| `/code` 機能の破壊 | 低     | 高   | 非破壊的更新、参照のみ                   |
| 循環参照           | 中     | 中   | 明確な階層（Skills → Shared → Commands） |
| EN/JAの乖離        | 高     | 低   | 既存のプロセス、新規ではない             |
| ユーザーの混乱     | 低     | 低   | 明確な構造、良いドキュメント             |

## 統合ポイント

### ADR 0001との関係

この ADR は ADR 0001 と同じパターンに従う:

- 薄いラッパーパターン
- モジュールベースの分離
- 参照ベースの統合
- 非破壊的更新

**一貫性**: `/code` と `/fix` は同じアーキテクチャに従う。

### 将来のコマンドとの関係

このアーキテクチャにより以下が可能:

- `/hotfix` モジュール化（必要な場合）
- 新しい TDD ベースのコマンド
- 共有 TDD 基礎
- 一貫したユーザー体験
