# docs/wiki

実装者が「今このプロジェクトではどうやるか」を引く場所。`docs/decisions/` の DR が決定とその根拠を不変の記録として残すのに対し、ここは決定が生んだ現在の姿を書く。DR は正準で、ここはそこから派生した写し。4 つの文書の分担と 8 つのルーティング規則は `docs/decisions/0106-adopt-the-wiki-as-the-current-state-view-over-immutable-drs.md` が持つ。

| 文書           | 何を読むために開くか                       |
| -------------- | ------------------------------------------ |
| `rules/`       | 常に守る言語 / ドメインの指令              |
| `docs/decisions/` | なぜこの形なのか。覆してよいのか        |
| `CLAUDE.md`    | このプロジェクトは何か                     |
| `docs/wiki/`   | 今どうやるか                               |

## ページの種類

1 共通項 1 ページで、各ページは 内容 → 定型手順 → 参照コード → 由来 → 根拠 の順。由来は共通項が派生した DR への参照で、その DR が supersede されたらページの書き換えが必要になる密接なものだけ張られる。根拠が 1 件だけの共通項は `_candidates.md` に置かれ、2 件目が現れたらページへ昇格する。初出でも根拠が 2 件揃っていれば直接ページになる。1 回の run が動かすページ数には上限があり、昇格できるのに溢れた分は `_candidates.md` の昇格待ちへ回って次の run で先に処理される。

`kind: structure` を持つページは共通項ではなく、1 つの glob 契約グループの構造を書く。グループとは、同じ境界と契約を共有するファイルの集まりで、`globs` が表す単位そのもの。`workflow-structure.md` が `**/workflows/**/*.js` の 7 ファイルを 1 枚に収めるのはそのため。節は 内容 → 境界 → 契約 → 要求 → 参照コード → 由来 で、定型手順 と 根拠 は持たない。根拠 2 件の閾値もページ数の上限も掛からない。DR とコードから起こして人がレビューする。共通項ページと同じ glob を持ってよいが、共通項ページが述べた内容は書かずページ名で参照する。

由来節を張る条件は 2 種類で違う。共通項ページは密接な DR が無ければ節ごと持たない。構造ページは見出しを必ず持ち、条件を満たす DR が無いときは中身が空になる。6 節の並びを `skills/scribe/tests/skill_contract_test.py` が完全一致で固定しているため。

## 育て方

`/scribe` スキルまたは定期巡回の scribe が、closed になった PR / issue から自動で抽出する。初回は全履歴を読んで基礎化し、以降は前回の scribe PR マージ以降に closed になった分から増分更新する。追加 / 修正は PR で提案されるので、レビューしてマージする。マージが承認になる。手動追記も可。

由来が指す DR が supersede / deprecated / rejected へ動いたときは、その status を動かす変更単位でページを書き換える。リンクの張り替えだけでは足りず、本文の記述が今も成り立つかを status を動かす人が見る。リンク側は `skill_contract_test.py` が検査する。
