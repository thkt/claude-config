# 着手後に崩れた前提の記録

## 内容

issue の本文が挙げた原因や前提は、着手して実物を読むと崩れることがある。崩れたまま実装を進めると、issue が解こうとした問題と PR が解いた問題がずれる。前提が崩れたら、その場で close コメントか PR 本文に「issue が書いた原因は正確でなかった」と何がどう違ったかを書く。issue 本文は直さない。読み手が辿るのは issue から PR への順序なので、訂正は下流に置く。

## 定型手順

1. 着手時に issue の原因欄と前提を、実物のコードと設定で 1 つずつ確かめる
2. 崩れた前提が見つかったら、実装より先に記録する場所を決める。issue が生きているなら close コメント、PR にするなら本文
3. 何を前提としていたか、実際は何だったか、その差で scope がどう変わるかを書く
4. 前提が全部崩れて解く問題が消えたら、実装せず close する

## 根拠

- #320 「着手後に前提のずれが判明したので記録する」。issue は「plan ごとに T-NNN を 1 から振り直す運用」を原因としたが、既存規約が求めるのは plan 全体の一意性までで、ファイル跨ぎの重複を禁じていなかった。規約違反ではなく規定の空白だった
- #387 調査の結果 issue の前提が成り立たないことが分かり、実装せず close した
- #246 「前提が未実測だった」。各 reviewer が 713 行を読むという根拠が、実際には Read を強制しないポインタ 1 行だったと分かり、分割の費用対効果が合わないとして close した
- #235 paths glob の実験で項目 3 の前提が変わり、項目の順序が入れ替わった
