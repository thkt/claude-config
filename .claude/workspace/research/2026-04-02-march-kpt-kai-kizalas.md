# 2026-04-02 thkt 3月 Daily KPT

## 対象範囲

- `sae` を使って、`2026-03-02` から `2026-03-27` までの `thkt` の daily 18 件を確認した
- 3月 daily のうち、`KAI` と `パノラマ（kizalas）` に関する記述を中心に整理した

## KAI案件

### Keep

- `3/2` に開発フロー改善を提案し、`3/3` の Weekly Planning まで報告をつなげられた。中身としては、PR フローの見直し、STG 確認フローの改善、パートナーの AI 実装状況の把握など、開発の進め方そのものを整える話が中心だった
- `3/3`、`3/17`、`3/24` にリリースを進められた。`3/3` は新機能からの cherry-pick を含むリリース、`3/17` は長引いたが完了まで持ち込み、`3/24` は予定機能を問題なく出せた
- `3/4` に媒体追加時の FE タスク分割を整理し、`3/10` にはタスクをサブタスクや issue に分解した。Weekly Planning では issue テンプレを AI に渡して起票する進め方も共有できた
- `3/5` の KAI 振り返りで、PR フロー改善の説明会と Claude Code 活用説明をやる方針を決められた。改善案を出すだけでなく、相手が使える状態まで持っていく動きに切り替えられた
- `3/5` に無断マージ問題を `Approved 必須化` という仕組みで防ぐ方向に進められた。「気をつける」ではなく、レビュー承認がないと進まない状態に寄せたのがよかった
- `3/11` に AI 設定の更新や、危ない変更に気づけるレビュー体制の議論を進められた。DB マイグレーションエラーをきっかけに、GitHub Actions 上で Claude レビューを回す話や、PR から気軽にレビューを呼べる運用の検討まで進んだ
- `3/13` に Notion トークン取得まで進め、AI に渡す文脈整備の土台を作れた。Read 権限で指定したノート情報を取り出して LLM に渡しやすくする方向性が見えた
- `3/17` には Notion の情報取得ツールをパートナーへ共有し、タスク共有・アサインと一緒に AI 活用の実績を少しずつ広げられた
- `3/24` に Statista MCP の `CancelledError` を切り分け、原因をクライアント初期化エラーまで絞れた。あわせて axon hooks の共有設定や使い方もチームに広げる準備を進めた
- `3/25` に Node.js セキュリティアップデートを横断対応し、`3/26` には Notion のプロジェクト概要整理、`kai` / `kai-api` の環境構築手順整備を含むオンボーディングドキュメントを作れた
- `3/27` に `ise-pl-app` のリロード時の引用記事欠損バグ修正 PR をレビューし、リードだけでなく実務面の支援も継続できた

### Problem

- 開発フロー改善の提案は、`3/2` 時点で着地点や相手の反応の想定が甘く、そのままでは着地しなかった。特に PR フローや STG 確認フローの改善は、何を変えたいのかは見えていても、どこまで合意を取りたいのかが曖昧だった
- `3/5` の振り返りでも、自分と相手の認識が揃っている前提で提案していたことが課題として再確認された。STG 確認フローの提案も、同じ問題意識を共有していると思い込んでいた
- ツールや AI ワークフローは、作るだけでは相手にとって「使える状態」にならず、説明会、チートシート、実際の使いどころの共有まで含めた導入支援が不足していた
- `3/10` にリリースフローの違和感には気づいていたが、その場ではスコープ外として流しており、改善までつなげ切れていなかった。運用上の違和感を issue や確認タスクに落とし切れていなかった
- `3/11` の DB マイグレーションエラー議論からも、危ない変更を早めに拾う品質ゲートがまだ弱かった。マイグレーションや大きめの差分に対するレビュー観点が個人依存だった
- `3/24` のリリース後は、フロントだけでは根本解決できないエラー増加があり、API 側依存の課題が残った
- `3/26` のオンボーディングドキュメントは、作成者本人の視点だけでは抜け漏れに気づきにくかった。実際、第三者レビューを通さないと、パートナーがつまずくポイントや前提知識の不足を見落としやすかった

### Try

- 提案を持ち込む前に、「今回どこに着地させたいか」「何を合意できれば成功か」「相手が何を懸念しそうか」を事前に言語化してから話す
- フロー改善や AI 活用は、提案だけで終わらせず、説明会・チートシート・小さな導入支援までセットで出す。特に PR フローや Claude Code 活用は、実演ベースで共有する
- リリース運用で違和感が出たら、その場で `issue化 / オーナー決定 / 次回までの確認項目整理` までやる。スコープ外として流して終わらせない
- マイグレーションや危険度の高い変更は、レビュー観点を明文化し、品質ゲートや自動レビューの対象に寄せる。たとえば DB 変更、hook 設定、リリース前確認を重点観点として固定する
- API 側依存の問題は、フロントで抱え込まず、早めに「どこまで切り分けたか」を添えて連携する
- オンボーディングドキュメントは、パートナーや第三者レビューを前提にし、最初からレビュー依頼の流れまで含めて進める。環境構築手順や前提知識は特にレビュー対象として明示する

## パノラマ（kizalas）案件

### Keep

- `3/3` に施設管理フロア絞り込みバグを調査し、`floor_id` のフィルタリング問題が原因だと特定できた
- `3/9` に依頼修正へ対応し、クーポン・NEWS 複製 issue の作成、夜間通知の時間帯判定修正の実装と PR 作成まで進められた
- `3/11` に `Issue #510` の夜間通知ロジック修正を完了し、browser-agent のスクリーンショット確認を使って挙動確認まで行えた
- `3/17` にパノラマ側とのタスク調整を継続し、`3/23` にはブランチ整理や Slack 依頼対応も進められた
- `3/18` と `3/25` に Node.js セキュリティ対応を進め、`fast-xml-parser` を含む脆弱性影響の調査、共有文面の準備、`kizalas` のアップデート PR 作成まで出せた
- `3/26` に複製ボタン不具合の調査、コードレビュー、クリーンアップ、請求・報告関連までまとめて対応できた。調査内容も、単なる見た目ではなく遷移時エラーやブラウザバック後の読み込み不具合まで見られていた
- `3/27` にニュース・クーポン詳細の複製機能追加、stg/本番の favicon 切り替え、`useFetch` の AbortError 修正と一部 revert、バックエンドへの環境変数依頼まで進められた

### Problem

- `3/9` の時点で、AI を使ったブラウザ確認はセレクトボックス表示やスクリーンショット確認の精度に限界があった。見えているものを撮るだけでは、確認したい状態を十分に検証できなかった
- `3/26` に、見た目修正を AI に依頼するときは画像だけでは足りず、色やサイズなどをテキストで具体化しないと伝わらないことが分かった。GitHub issue 上の画像を AI がそのまま使えない前提も考慮が必要だった
- `3/27` の AbortError 対応では、最初に見えていた現象に引っ張られ、問題の本質が「破棄する」後の挙動にあることを掴むまでに回り道があった。ブラウザバック自体が本質ではなかった

### Try

- UI 確認は AI スクリーンショット確認だけに寄せず、見るべき状態や確認ポイントを先に列挙してから検証する。特にセレクトボックスやダイアログ遷移は手順を明示する
- 見た目修正の issue には、画像添付だけでなく、色・サイズ・余白・文言などをテキストで必ず書く。AI に作業させる前提の issue として書く
- 不具合調査では、最初の見え方ではなく「どの操作の後に壊れるか」を状態遷移で切り分けてから修正に入る。ブラウザバック、ダイアログ操作、キャッシュ削除などの条件を分けて追う
- フロントだけで閉じない変更は、環境変数やバックエンド対応を早めに依頼して、待ち時間を減らす
