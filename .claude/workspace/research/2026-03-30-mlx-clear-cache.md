## Summary

There are two distinct "clear cache" functions in the MLX C API. `mlx-rs` v0.25.3 wraps only one of them. The memory-related `mlx_clear_cache()` is **not exposed** in the Rust API but is accessible via the `mlx_sys` FFI bindings. `rurico` currently uses neither.

## Findings

### Two different cache-clear functions in MLX C API

| C function | Header | C++ maps to | What it clears | mlx-rs wrapper |
|---|---|---|---|---|
| `mlx_clear_cache()` | `mlx/c/memory.h` | `mlx::core::clear_cache()` | Metal GPU buffer cache (unified memory) | **None** (not wrapped) |
| `mlx_detail_compile_clear_cache()` | `mlx/c/compile.h` | `mlx::core::detail::compile_clear_cache()` | Compiled function graph cache | `mlx_rs::transforms::compile::clear_cache()` |

### Full memory API in mlx-sys (available via FFI)

All functions from `mlx/c/memory.h` are generated by bindgen and available in `mlx_sys`:

| `mlx_sys` function | Purpose |
|---|---|
| `mlx_clear_cache()` | Release cached Metal buffers back to the system |
| `mlx_get_active_memory()` | Currently allocated GPU memory (bytes) |
| `mlx_get_cache_memory()` | Cached (reclaimable) GPU memory (bytes) |
| `mlx_get_memory_limit()` | Hard memory limit |
| `mlx_get_peak_memory()` | Peak memory watermark |
| `mlx_reset_peak_memory()` | Reset peak watermark |
| `mlx_set_cache_limit()` | Set max cache size (returns previous) |
| `mlx_set_memory_limit()` | Set hard memory limit (returns previous) |
| `mlx_set_wired_limit()` | Set wired memory limit (returns previous) |

### mlx-rs compile::clear_cache misleading doc

[->] The `mlx_rs::transforms::compile::clear_cache()` doc comment says "Clear the memory cache" but actually calls `mlx_detail_compile_clear_cache()` which clears the **compilation** cache, not the Metal memory buffer cache. This is a misleading docstring in the upstream `mlx-rs` crate.

[compile/mod.rs:176-181 in mlx-rs-0.25.3]

### rurico current state

- [check] `rurico` does not call any cache-clearing function.
- [check] `Embedder` wraps `EmbedderInner` in a `Mutex`. No custom `Drop` implementation.
- [check] When `Embedder` is dropped, the `ModernBert` model (and all its `Array` weights) are dropped via standard Rust drop. `mlx-rs` `Array` has a `Drop` that calls `mlx_sys::mlx_array_free()`.
- [->] Array drop releases the reference but does not guarantee immediate Metal buffer deallocation -- buffers may remain in the MLX cache for reuse.

### Downstream impact

- [check] `yomu` and `recall` (downstream CLIs) do not call any cache-clearing function either.
- [->] For CLI tools that create an `Embedder`, run a batch, and exit, the OS reclaims all memory on process exit. Cache clearing matters primarily for long-lived processes or when memory pressure is a concern.

### Disconfirmation check

Searched for evidence that `Array::drop` already calls `mlx_clear_cache` internally. It does not -- `mlx_array_free` decrements the reference count but freed buffers go to the MLX allocator cache, not back to the system. `mlx_clear_cache()` is the only way to force buffer deallocation to the system while the process is running.

## How to use mlx_clear_cache from rurico

If needed, the function can be called directly via `mlx_sys`:

```rust
pub fn clear_metal_cache() {
    unsafe { mlx_sys::mlx_clear_cache(); }
}
```

No additional dependencies needed -- `mlx_sys` is already a transitive dependency through `mlx-rs`.
