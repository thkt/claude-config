# 文章レビュー

文脈を共有し、リンク先を開けるチームメイトに向けて書く。Issue 本文には差分だけを書き、背景はリンク先に置く。読み手の判断を変える行だけを書く。このレビューが確認するのは Issue 本文の構成だけ。

## 構造

| チェック       | 質問                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 問題の提示     | 冒頭の 1〜3 行で、問題または要望を説明しているか                                                                                      |
| 具体性         | bug では再現手順を、feature ではユースケースを具体的に書いているか。期待結果を読み手の推測に委ねていないか                            |
| 差分への集中   | コードから読み取れる what を省き、why と完了条件に絞っているか。本文に収まらない内容は削除するか、別 issue またはリンクへ移しているか |
| セクション適合 | 各セクションには、その見出しが求める内容だけを書いているか                                                                            |
| 推測の混入     | 本文の各記述が、誰かが決めた判断または誰かが確認した事実か。推測は AskUserQuestion または Read で確認してから書いているか             |

## 冗長パターン

下表にない冗長さでも、同じ性質であれば修正する。

| パターン       | 修正                                                                                           |
| -------------- | ---------------------------------------------------------------------------------------------- |
| リンク先の転記 | リンクした文書やログを再説明せず、リンクと要点 1 行にまとめる。本文には差分だけを書く          |
| 決定の重複     | 同じ設計理由は、その判断を記す箇所で 1 回だけ述べる。案の比較は本文に書かず、`/think` に委ねる |
| AC の過剰指定  | criterion は残し、story 名や設定値の列挙など、記述方法の指定は削除する                         |
