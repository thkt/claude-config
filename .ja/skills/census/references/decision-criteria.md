# /census 判定基準

Phase 4 のタグ付け、ランク付け、`critic-design` challenge で使う。Phase 4 の Step 2 で `critic-design` に全文を渡す。

## incomplete-contract

`incomplete-contract` は、コードのコメントが「何が真か」を述べる一方で「何が真であり続けるべきか」を述べていない検出事項。読み手が「この状態は維持すべき」と推測することに依存し、セキュリティ不変条件や設計根拠で頻出する。欠けた将来向けのルールは DR でしか補えないため、`documented?` の値に関わらず強い DR 候補とする。

例えば、SSRF-safe な HTTP クライアントのフィールドに「redirect disabled for SSRF」というコメントがある一方、「ユーザー URL を扱う将来のコマンドはこのクライアントを必ず使用する」というルールが欠けているケースがこれにあたる。

## DR 化価値の経験則

DR にするのは、ツールが守れない次の 2 つに限る。lint 設定、型システム、自動テストは機械的に判定できる違反をその場で弾くが、DR の文章は読まれたときにしか効かない。事実を宣言する設定 (`deny.toml`、`Cargo.toml`) はそれ自体が唯一の正で、DR へ複製すると両者がずれる。設定の方針は設定ブロックへ 1〜2 行のコメントで書く。

| カテゴリ                     | 例                                                           |
| ---------------------------- | ------------------------------------------------------------ |
| ツールで強制できない不変条件 | フィールド X と Y が同型で、両者を同時に使ってはいけない制約 |
| 公開 API の互換性の約束      | exit code の規約、JSON 出力のスキーマ                        |

## impact + reversibility 基準

| Impact | 判定基準                                                        |
| ------ | --------------------------------------------------------------- |
| H      | モジュール境界を跨ぐ公開 API に影響、2 つ以上サブシステムを支配 |
| M      | 単一モジュールの内部契約                                        |
| L      | 局所的なスタイル / 命名                                         |

| Reversibility | 判定基準                                               |
| ------------- | ------------------------------------------------------ |
| high          | 1 箇所の編集で巻き戻し可能                             |
| medium        | 2〜5 ファイルの連動した編集が必要                      |
| low           | マイグレーション / 非推奨サイクル / スキーマ変更が必要 |

## Devil's Advocate challenge の観点

`critic-design` は初期昇格候補の各々に以下で挑む。

- 将来の貢献者はそのルールで本当に得をするか。読み手は誰か
- コメント + テスト、事実を宣言する設定、型システム、lint といった非 DR の機構が既に守っているなら、DR は冗長にならないか
- DR がロックインを生むリスクは無いか。進化すべき決定を過剰に文書化していないか
- モノリシック境界の候補の場合、DR が現状維持を正当化し、分割への圧力を弱めないか
- バグと不変条件のどちらか。現コードが誤りで変更すべきなら、bug-fix の後続として提示し DR にしない。現コードが意図的で保持すべきなら DR 化を検討する。誤った挙動を意図的と文書化しない

## Verdict

最終候補リストは `keep` と、吸収先 DR を明示した `downgrade` で構成し、`drop` は除外する。

| 判定        | 意味                                                                                                       |
| ----------- | ---------------------------------------------------------------------------------------------------------- |
| `keep`      | DR 化に値する。単独 DR または関連候補と統合して起票                                                        |
| `downgrade` | 単独 DR ではなく、関連 DR 内のセクションに吸収またはコメント強化                                           |
| `drop`      | DR 不要。設定 / コメント / テストで既に守られている、コストが価値を上回る、または bug-fix の後続に回す bug |
