# PR の書き方

PR のタイトルをどう決め、本文の骨格をどう選び、各節に何を書くか。`/pr` の Phase 2 と build workflow の Ship が読む。

## タイトル

- Issue 参照があれば Issue タイトルをそのまま使う
- 無ければ 72 文字以内で、命令形の動詞から始める
- `feat:` や `fix:` のような prefix は付けない。Issue タイトルにあれば外す

## 骨格の選び方

`gh pr create` は骨格を自動では適用しない。読み取って本文へ組み込む。

リポジトリに PR テンプレートがあればそれを使う。無ければ、このファイルから見て `../templates/pr.md` を使う。リポジトリ側は大文字小文字を区別せず、次の順に探して最初に見つかったものを採る。

1. `.github/pull_request_template.md`
2. `pull_request_template.md`
3. `docs/pull_request_template.md`
4. `PULL_REQUEST_TEMPLATE/` ディレクトリ

## 言語

`~/.claude/settings.json` の `language` が指す言語で本文を書く。未設定なら英語。コード、識別子、技術用語は翻訳しない。

## 節の並び

読み手が速く掴める順に並べる。解こうとしている問題と到達する状態を先に置く。次に何を変えたかと方針、最後にレビューの重点。

## 各節の中身

確かめていないことを書かない。各節の OK と NG の例は `../templates/pr.md` の ガイドライン にある。リポジトリ側の骨格を採った場合も同じ基準で書く。

| 節               | 書くこと                                                          |
| ---------------- | ----------------------------------------------------------------- |
| Changes          | diff から理由が読めない変更だけ。ファイルの目録は書かない         |
| Review focus     | 骨格に該当する節があればそこへ、無ければ `## Review focus` を作る |
| Design Decisions | 同等の代替から明示的に選んだ判断。無ければ節ごと省く              |
