# 仮説の消去 - 実例

問題提起は具体的かつ観察可能であること。「ダッシュボードのロードに 5 秒かかる」は分析できる。「アプリが遅い」はできない。

## 例。ダッシュボードのロードに 5 秒かかる

差分比較。他の画面は 300ms で返る。違いは `/api/dashboard` だけが 15 テーブルを引くこと。

| 仮説                           | 検証                             | 結果                 |
| ------------------------------ | -------------------------------- | -------------------- |
| N+1 クエリが出ている           | クエリログを数える               | 単発。消える         |
| index が欠けている             | 遅いクエリを EXPLAIN             | index を使う。消える |
| mount 時に全モジュール分を取得 | 取得列と描画に使う列を突き合わせ | 未使用の列が 8。残る |

Root cause は mount 時の一括取得。修正はセクションごとの lazy loading と必要時取得。同じ一括取得が他の画面にもあれば Pattern は Recurring。

## 例。フォームが 2 重送信される

差分比較。他のフォームは pending で disabled にする。このフォームだけ handler の中で `isSubmitting` を立てる。

| 仮説                                  | 検証                         | 結果                |
| ------------------------------------- | ---------------------------- | ------------------- |
| StrictMode が handler を 2 回呼ぶ     | 単発クリックで再現するか     | 再現しない。消える  |
| 親子でイベントが二重発火している      | ハンドラにログを入れて数える | 発火は 1 回。消える |
| state 反映前に 2 回目のクリックが入る | 連打で再現するか             | 再現する。残る      |

Root cause は state が反映される前に 2 回目を受けること。修正は即時に立つ `useRef` のフラグ、または form action からの `disabled={pending}`。同じ書き方のフォームが他にあれば Pattern は Recurring。

## 3 つ揃わないとき

仮説が 2 つしか出ないなら、差分比較の粒度が粗い。変更を 1 つずつ戻す、入力を 1 項目ずつ変える、環境を 1 つずつ揃える、のいずれかで違いを細かく切り出す。
