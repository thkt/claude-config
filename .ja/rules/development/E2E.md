# E2E

E2E はブラウザからシステム全体を通してユーザーの動線を検証する層で、実行と維持のコストが最も高い。主要動線に絞った小さなスイートを、失敗が常に意味を持つ状態で保つ。テスト全般の方針は TESTING.md に従い、ここでは E2E に固有の判断だけを扱う。

## E2E に置くもの

置くかどうかは 1 つの問いで決める。その壊れ方は、システム全体を動かして初めて見えるか。下位層で捕まえられるなら下位層に書き、E2E スイートはそのままにする。

| 検証したいこと                                 | 置く層               |
| ---------------------------------------------- | -------------------- |
| デプロイの破損、単体では正しい部品同士の連携   | E2E                  |
| バリデーションの分岐、条件による表示の切り替え | コンポーネントテスト |
| 計算、判定、変換のロジック                     | ユニットテスト       |

E2E を主要動線だけに絞る原則は、渡した先の層が実在して初めて成立する。絞る前に、その層がこのプロジェクトにあるかを確認する。無ければ、絞るのでなく下位層を作る。

## カバーの確認

E2E のカバーはリスクの地形でなく、書きやすさの地形に沿って積もる。最初から画面に見えているコントロールは覆われ、state で出現する要素 (エラーバナー、確認ダイアログ、0 件表示) と、認証や外部 SDK のように準備が重い経路が空白になる。

確認は層の名前でなくケースの単位で行う。「ユニットテストがある」で足りたことにせず、「未確認ユーザーがログインすると再送 UI が出る」のようなケースを挙げ、それを守っているテストのファイル名を確かめる。挙げられなければ未カバーとして扱う。

## スイートを走らせる場所

CI の中でスタック一式を起動できるかで分かれる。起動できるなら PR ごとに実行し、デプロイ済み環境が要るならリリースの確認として実行する。

| 前提                            | 実行契機                 | リトライ | 失敗の扱い                                 |
| ------------------------------- | ------------------------ | -------- | ------------------------------------------ |
| CI 内でスタック一式を起動できる | PR ごと                  | 0 回     | 落ちたらその PR で直す                     |
| デプロイ済み環境が要る          | デプロイ後のリリース確認 | 有効     | ロールアウト停止か切り戻しの判断につなげる |

デプロイ後に実行する構成では、実行するシナリオを環境ごとに選ぶ。データを作るシナリオと外部サービスを呼ぶシナリオはステージングに対して実行し、本番では読み取り中心のスモークに限る。この制限はパイプラインの設定でなくテスト自体に書き、パイプラインが変わっても残るようにする。

## 待機と assert の規律

flaky の主因は待ち方にある。個々の書き手の裁量に任せず、待機を Page Object へ閉じ込めて機械的に守らせる。

| 書かない形                                                 | 置き換える形                                | 書かない理由                                                       |
| ---------------------------------------------------------- | ------------------------------------------- | ------------------------------------------------------------------ |
| 固定時間の sleep (`waitForTimeout`)                        | 状態の待機 (web-first assertion)            | 所要時間の推測は両方向に外れ、短ければ落ち長ければ全体が遅くなる   |
| 同期 read の戻り値を静的に assert (`innerText` + `expect`) | auto-wait matcher (`toContainText`)         | snapshot 時点で値が未確定でも、偶然一致すれば通る                  |
| 不在の assert 単独 (`not.toBeVisible` / `toHaveCount(0)`)  | 先に現れるはずの要素を待ってから不在を確認  | ロード中は要素が 0 個なので、描画される前の瞬間に成立する          |
| 再取得を伴う操作 (ソート、フィルタ) の直後に表示を assert  | 操作の前にレスポンス待ちを仕掛けてから実行  | 再取得後の表示が直前と一致すると、反映前に成立して次が古い値を読む |
| 完了通知が出ない操作を完了側だけで待つ                     | 処理中インジケータの出現と消滅を 2 段で待つ | 処理が始まらず即終了した場合を見逃す                               |

## 要素の特定

ユーザーが知覚するもの、つまりロール、アクセシブルネーム、ラベルで特定する。CSS クラスと DOM 構造は実装の詳細であり、スタイリングやリファクタによって挙動と無関係に変わる。

`data-testid` を使う場合は文字列を定数へ集約し、Page Object からだけ import する。spec には locator を直接書かず、locator と操作と待機を Page Object へ閉じ込め、spec はシナリオの記述に徹する。

## テストデータ

各テストが自分専用のデータを用意し、自分が作ったものだけを検証する。他のテストが残した状態を読むテストは、単独でも並列でも異なる順序でも実行できない。

| 決め       | 内容                                                                                  |
| ---------- | ------------------------------------------------------------------------------------- |
| 用意の経路 | UI 操作でなく DB への直接 INSERT かテスト支援 API                                     |
| 命名       | 識別できる固定プレフィックスと、一意なサフィックスの組み合わせ                        |
| 後片付け   | 派生レコードとファイルまで teardown で回収し、UI 操作で生まれたものは明示的に登録する |
| 事前検証   | 投入したデータを UI 操作の前に schema で検証し、アプリの不具合と区別できる印で落とす  |

## 認証

setup で権限ごとに一度だけログインし、`storageState` に保存して各テストが読み込む。全テストが冒頭で UI からログインする構成は遅く、ログイン画面が変わるとスイート全体が一斉に落ちる。並列 worker が同一アカウントを取り合うなら、ロールごとにアカウントを複数用意する。

## 画面と権限のマトリクス

主要画面が各権限で表示されることの確認はマトリクスなので、1 マスずつ手で書かず、画面の一覧と閲覧できる権限をデータとして定義してループで生成する。許可された権限では画面の見出しが表示され、許可されない権限ではフォールバック先に着地することを、同じ一覧から両方向で検証する。画面や権限の追加は一覧への 1 行の変更で済み、誤った権限への公開も同じスイートで落ちる。

## 外部サービスとの境界

外部サービスを呼ぶ口をスタブで固定し、UI から到達できない状態の準備と観測はテスト支援 API で行う。E2E ではバックエンド全体が検証対象なので、固定する境界はその先、チームの制御下にないサービスを呼ぶ縁に置く。

スタブとテスト支援 API は本番へ置かない。アカウント作成、認証コード発行、メール読み取りができる口を、ユーザーが到達できる場所へ出さない。

スタブは提供元の変更で乖離し、実際の連携が壊れているのにスイートが通る状態を作る。スタブは実際に読むエンドポイントとフィールドだけに絞り、実連携を通すシナリオを少数、ステージングで維持する。

メールの到達のようにブラウザの外で起きる事象は web-first assertion の守備範囲外なので、上限付きのポーリングで待つ。

## flaky の扱い

欠陥が無いのに断続的に落ちるテストは、気づいた日に直すか隔離する。隔離は `test.fixme()` でリリースの確認から外し、修正を課題として起票する。リトライで通ったテストは成功として数えず、修正リストに載せる。

## 失敗の証跡

デプロイされた環境での失敗は手元で再現しにくいので、証拠を実行時に採取する。失敗した実行の trace を保存し、長いシナリオは `test.step` で段階に分けて、どの段階で落ちたかが分かるようにする。
