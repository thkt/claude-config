# Testing

カバレッジの観点/優先領域/テスト命名/delta-based gate を扱う。

## プロジェクトの決めが先

テスト方針はプロジェクトの `.claude/rules/development/TESTING.md` > グローバルの `~/.claude/rules/development/TESTING.md` の順で読む。グローバル側は既定値であり、プロジェクト側が触れていない観点だけをそこから補う。どこまでの異常を許容するかは、実装ごとの判断でなくプロジェクトの合意として決める。

## Coverage は補助指標

カバレッジは「コードが実行されたか」を測る指標であり「何を検証したか」までは測らない。数値を目標にせず、観点と優先領域を目標にする。

| Level | 名称     | 基準                                           |
| ----- | -------- | ---------------------------------------------- |
| C0    | 命令網羅 | 各行を少なくとも 1 回実行                      |
| C1    | 分岐網羅 | if/switch の両側を実行                         |
| C2    | 条件網羅 | 複合条件の各オペランドを true/false 両方で実行 |

## 優先領域

全領域を一律検証せず、影響の大きい領域ほど深く検証する。ここでの深度とは、その領域で到達すべき検証レベルを指す。故障が金銭損失/認可漏れ/データ消失に直結する領域は C2 とする。C1 の領域であっても、複合条件 (&&/||/三項演算子) を含む箇所は C2 へ引き上げる。

| 領域               | 例                           | 深度 |
| ------------------ | ---------------------------- | ---- |
| 業務ルール中核     | 計算/判定/変換ロジック       | C2   |
| 権限制御           | ロール判定/認可              | C2   |
| 課金・請求         | 金額計算/レート判定          | C2   |
| データ整合性       | トランザクション/unique 制約 | C1   |
| ステータス遷移     | 状態マシン                   | C1   |
| ユーザー導線       | 予約/決済                    | C1   |
| 表示コンポーネント | props レンダリング           | C0   |
| 薄いラッパー       | 委譲のみ                     | C0   |

## テスト作成の順序

観点から始めて、カバレッジは漏れ検出にだけ使う。

1. テスト対象の仕様を読み、満たすべき条件を列挙する
2. シグネチャとドメインに該当する観点を観点チェックリストから選ぶ
3. 条件 (Step 1) と観点 (Step 2) を満たすテストを書く
4. カバレッジを実行し、未通過の分岐/条件には対応する観点でテストを追加する

### 観点チェックリスト

| 観点         | 確認内容                                                                                       |
| ------------ | ---------------------------------------------------------------------------------------------- |
| 同値分割     | 同じ振る舞いになる入力をグループ化し、各グループの代表値 1 つをテスト                          |
| 境界値       | 各境界の両側 (min - 1 と min、max と max + 1)。ゼロと空も特異値として加える                    |
| 分岐 (C1)    | 各 if/switch の全経路                                                                          |
| 条件 (C2)    | 各複合条件のオペランドごとに true/false                                                        |
| 組み合わせ   | 独立した条件が 2 つ以上絡むなら、デシジョンテーブルを書いて各行をカバー                        |
| 状態遷移     | 許可される遷移は通り、禁止される遷移は拒否されることを確認                                     |
| 異常系       | 不正入力/null を与えて例外パスを通し、返るエラーの種別 (ステータスコード/エラー型) まで assert |
| 環境異常     | タイムアウト/接続失敗/レートリミット/想定外のレスポンス形式。外部依存を呼ぶときだけ適用        |
| 事故パターン | 二重送信/タイムゾーン/権限バイパス/中途半端な状態など、プロダクトで起きうる事故                |
| 並行性       | 競合/順序依存。対象が async/multi-threaded のときだけ適用                                      |

## テスト命名

テスト名は検証する仕様を条件と期待結果で述べる (例: "amount が負のとき deposit を拒否する")。あるべき名前は、実装をリファクタしてもそのまま通用する名前。名前に実装の語彙 (メソッド名/内部手順) が入っていたら、ドメインの条件と期待結果の語彙に置き換える。

## バグ修正の再現テスト

バグ修正は、原因を直す前にそのバグを再現するテストを 1 件追加し、Red を確認してから修正に入る。修正後は全スイートを実行し、再現テストが green に変わりリグレッションが残っていないことを確認する。

## テストが観測するもの

テストの価値は、何を壊したときに落ちるかで決まる。対象の種別ごとに到達可能な最上段が決まり、その段でテストを書く。

| 段 | 観測するもの                       | 捉える退行                       | 捉えない退行                       |
| -- | ---------------------------------- | -------------------------------- | ---------------------------------- |
| 1  | 成果物を動かした出力               | 判定、停止、返り値、検出率の変化 | 文書の体裁                         |
| 2  | 2 つの成果物の間で値が一致すること | 片側だけ変えたときのずれ         | 両側を同時に変えたとき             |
| 3  | 1 つの文書の中の節、並び、語       | 節の消失、順序の逆転             | 構造の破壊、意味の反転             |

実行主体を持たない文書に段 1 は無く、対応物を持たない文書に段 2 は無い。

| 対象                                  | 到達可能な最上段 | 理由                                                     |
| ------------------------------------- | ---------------- | -------------------------------------------------------- |
| hook (`.py` / `.sh`)                  | 1                | プロセスを起動して stdin から stdout を観測できる        |
| workflow スクリプト                   | 1                | スタブ実行で phase、停止、返り値を観測できる             |
| skill の `scripts/`                   | 1                | CLI として stdin から stdout を観測できる                |
| reviewer skill と reviewer agent 本文 | 1                | corpus と `review_score.py` で Recall と FP Rate が出る  |
| それ以外の skill 本文                 | 2                | 実行が LLM 依存で非決定。対応物との照合が上限            |
| `rules/` と `docs/`                   | 3                | 実行主体を持たない                                       |

広い網の例として、退役した記法の再登場を防ぐために一般的な英単語を文書全体で禁止する形がある。無害な 1 文が落とすので、退役した記法の並びそのものを対象にする。

| 禁止                                                     | 代わりに書くもの                                     |
| -------------------------------------------------------- | ---------------------------------------------------- |
| 到達可能な段より低い段で書く                             | 対応物や実行経路を探し、上の段で書く                 |
| 低い段の主張に、上の段でしか正当化できない広い網をかける | 主張の形に合わせて網を絞る                           |

## 段 1 の実行契機

reviewer の精度計測は CI では走らない。実行は人が行い、CI が検査するのは記録の新しさである。記録が 1 件も無い skill は未計測として扱い、走らせるか corpus ごと退役させるかを決める。

| 要素   | 内容                                                                                          |
| ------ | --------------------------------------------------------------------------------------------- |
| 契機   | reviewer の定義、skill 本文、corpus のいずれかが変わったとき                                  |
| 実行   | `skills/_lib/review-harness.md` の blind 手順で走らせ、`test/results/` に記録を 1 件足す      |
| ゲート | 最新の記録がその 3 つの内容ハッシュを持ち、現在のハッシュと一致すること                       |
| 対象   | corpus を持つ reviewer skill のすべて                                                         |

## テストが空振りしていないか

テストは書いた直後に壊して落ちることを確認する。壊し方は、そのテストが守る対象を実際に壊す形を選ぶ。

| 壊し方の型               | 内容                                                                                                |
| ------------------------ | --------------------------------------------------------------------------------------------------- |
| 検査対象を成果物から作る | 骨格から本文を組んで骨格と照合するなど。改名すると両側が同時に変わり、どの改名でも通る              |
| 前提の欠落が空を返す     | 解析に失敗すると必須項目が 0 件になり、比較する相手が消えて全て通る                                 |
| 別のテストが落ちる       | 壊した箇所を fixture に使う別テストが落ち、対象のテストは通ったままになる。落ちたテスト名を必ず読む |

## テストダブルの優先順位

依存は実物に近いほど統合のずれを捕える。下記の優先順で選ぶ。上位を使えない理由 (遅い/外部副作用/非決定的) があるときだけ下位に落とす。assert の対象は観測可能な振る舞い (戻り値/状態変化) に置く。呼び出し自体を検証してよいのは、呼び出しそのものが仕様である外部への副作用に限る。通知送信や監査ログのように、戻り値と状態のどちらからも観測できないものが該当する。それ以外の呼び出し検証は、戻り値か状態の assert に置き換える。

| 種別 | いつ使うか                                            |
| ---- | ----------------------------------------------------- |
| Real | 実物が十分速く副作用が閉じているなら最優先            |
| Fake | 実物が遅い/外部依存。軽量な動作実装で挙動ごと代替する |
| Stub | 戻り値だけ固定できれば足りるとき                      |
| Mock | 呼び出し自体 (回数/引数) の検証が目的のときだけ       |

## Coverage Gate

PR で C0/C1 を下げない。評価は差分ベースで行い、絶対値の下限は設けず、数値を目標化しない。絶対値が必要な場合は、非機能要件として定義する (例: セキュリティツールで C0 が 90% 以上)。例外は、自動生成コード/データ定義/テストファイル/移行中のレガシーコード。
