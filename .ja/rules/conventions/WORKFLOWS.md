# Workflow Conventions

`workflows/` 配下の workflow スクリプトに対する規約。

## 命名とファイル配置

`workflows/` 直下だけを読み、`.js` が workflow として登録される。スクリプト内のプロンプト文字列は LLM が読むので、PROSE.md の文長規約に従う。

| 対象                   | 規則                                                                                          |
| ---------------------- | --------------------------------------------------------------------------------------------- |
| スクリプトのファイル名 | `workflows/<name>.js`。`<name>` がそのまま `Workflow({name})` で解決される名前                |
| name の形              | 英単語 1 語。helper, utils, tools のような汎用名は使わない                                    |
| 補助スクリプト         | `workflows/<name>/` へ置く。直下へ `.js` を置くと、補助のつもりでも workflow として登録される |
| 共有ハーネス           | `workflows/_lib/` へ置く。テストから import する用途に限る                                    |

## 参照記法

同梱資材を指すパスは、開発ツリー (`~/.claude`) とプラグイン配布 (`~/.claude/plugins/` 配下) の両方で解決する形で書く。`bundled` の探索は `.ja/` を除外する。定義はスクリプトごとに複製されるので、変えるときは持っているスクリプトすべてを同じコミットで変える。

| 参照する対象                                                | 書き方                                      | 理由                                                              |
| ----------------------------------------------------------- | ------------------------------------------- | ----------------------------------------------------------------- |
| 同梱のスクリプト、テンプレート                              | `bundled(rel)` をスクリプト内で定義して使う | 開発ツリーを先に試し、無ければ plugins 配下を find で拾う         |
| 実行環境側のファイル (`settings.json`、出力先の `history/`) | `$HOME/.claude/<path>` を直書き             | 配布物ではないので、プラグイン配布下でも同じパスに実体がある      |
| 別モジュール                                                | 読み込めない                                | スクリプトが 1 つの関数本体として評価され `import` を書けないため |

## 引数とプロンプトの受け取り

`args` は文字列とオブジェクトの両方を受ける。文字列は短縮記法で、何を指すかはスクリプトごとに決める。`repo` が任意なら、空のときプロンプトをそのまま返す。必須なら常に足す。

| 対象                      | 規約                                                                                                             |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| args の解釈               | オブジェクトはそのまま使う。文字列は `{` で始まるときだけ JSON として読み、失敗したら短縮記法として扱う          |
| 文字列オプション          | `typeof` で型を確かめ、`trim()` が空なら既定値へ倒す。差分の比較対象を指す `base` の既定値は `main`              |
| repo を受け取るスクリプト | `anchor(p)` を定義し、エージェントへ渡すプロンプトをすべて通す。anchor は `cd <repo> &&` を促す 1 文を先頭へ足す |

## degradation の記録

失敗や欠落した結果を、返り値にも `log()` にも喪失粒度を残さないまま捨てるか既定値へ倒す分岐を degradation と呼ぶ。喪失粒度とは、何が/いくつ/なぜ落ちたかを後から再構成できる情報 (件数、id、対象名、理由)。

主チャネルは workflow の返り値。スナップショットは audit workflow だけが持つ追加チャネル (DR-0047 の `docs/audit/` への書き出し) で、他の workflow は返り値へ記録する。`log()` は対話中の補完で、返り値だけでは人間が気づけない degradation を実行ログに残す。喪失粒度を返り値に残しているなら、同じ情報を `log()` へ二重に出すことは求めない。

| 状況                                               | 記録すべき粒度                          |
| -------------------------------------------------- | --------------------------------------- |
| エージェント応答がスキーマを満たさず既定値へ倒れる | 落ちた件数、対象 id、既定値を採った事実 |
| 結果の一部が欠落し、残りで続行する                 | 全体数に対する取得数、欠落分の識別子    |
| 失敗を握って fail-open で次のフェーズへ進む        | 検証できなかった対象、未検証である旨    |

## キャリブレーション

同じ fail-open でも、喪失粒度を残すかどうかで可否が分かれる。

- 残す。全 id が揃わず英語原文へ倒したとき、`${byId.size}/${slots.length} translated` を `log()` に出す
- 残さない。エージェント応答を空配列へ倒し、件数も理由も返り値にも `log()` にも書かない

## スクリプトの評価形式

スクリプトは 1 つの関数本体として評価されるため `import` を書けない。dynamic `import()` も起動前の構文チェックで `import() is not available in workflow scripts` を返して弾かれる。共通ロジックを別モジュールへ切り出す設計は採れないので、重複を見つけても括り出す前にこの制約を確かめる。

## スクリプトの解決タイミング

`Workflow({name})` はセッション開始時点のスクリプトを実行するので、同じセッションで直した版を走らせるには `Workflow({scriptPath})` を渡す。scriptPath が効くのは最上位だけで、入れ子呼び出し (`build.js` が code を呼ぶ形) は名前で解決する。入れ子で走るスクリプトを直したときは、最上位から直接走らせて確かめる。
