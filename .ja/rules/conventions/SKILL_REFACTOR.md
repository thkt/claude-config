# Skill Refactor

既存 skill を規約へ揃え直すときの順序。上から当てる。機械で拾えるものを読む前に潰すと、通読で探す対象が構造と文章だけに絞れる。

| 段階   | 見るもの                                                                  | 拾い方                       |
| ------ | ------------------------------------------------------------------------- | ---------------------------- |
| 1 機械 | 参照記法、`~` や `$HOME` の固定パス、見出し語彙、本文とリファレンスの行数 | grep と行数カウント          |
| 2 実在 | `${CLAUDE_SKILL_DIR}` の解決先、rules への参照、テンプレートの列          | パスを解決して存在を確かめる |
| 3 事実 | 前提として書かれた制約が今も成り立つか                                    | 参照先の現物を読む           |
| 4 構造 | Phase の並び、同じ操作の重複、分岐の合流先                                | 書き換えの前後で図に起こす   |
| 5 文章 | 意図と実行と判断の分離、散文の位置、1 文への詰め込み                      | 通読                         |
| 6 削除 | 重複した指示、自己説明、動かないコード、経緯                              | 通読                         |
| 7 固定 | 直した結合をテストで守る                                                  | 壊して落ちることを確認       |

## 段階ごとの判断

1 で拾うのは、正解が規約に書いてあって目視が要らないもの。バッククォートで囲んだ `${CLAUDE_SKILL_DIR}`、Phase 内の連番見出し、100 行超過が該当する。

2 は plugin 配布を前提に確かめる。`~/.claude/skills/<name>/` は開発ツリーを指すので、plugin として動く skill では自分自身でなく別のコピーを読む。

3 は「〜のため」と書かれた前提を疑う。agent の tools、CLI の挙動、ハーネスの変数展開は、書かれた時点から変わる。確かめられない理由は書かず、指示だけ残す。

4 はまず入力から出力までを図に起こす。分岐と合流、同じ操作が現れる回数は、番号順に読むだけでは見えない。図で確かめてから、系統でなく工程で並べ直す。入力の種類ごとに Phase を分けると番号が系統を跨ぎ、読み手が 2 つの流れを行き来する。同じ操作が複数の Phase にあるなら独立した Phase へ一本化する。組み替えた図をユーザーへ見せ、複雑さの出どころと減る Phase を示してから書き換える。

書き換えたら、もう一度図を起こす。行や手順を畳む編集は行数だけを減らすつもりでも経路を落とすので、どの状態にも入口と出口があるかを図で数える。テストは Phase 番号と参照先の食い違いで落ちるが、経路の欠落では落ちない。

5 は 1 つの節に 3 種類を混ぜない。実行は番号付き手順、判断は条件と扱いの表、意図は 1 文で先に置く。散文は表と bullet の前に集める。

6 で消すのは 3 つ。他の場所が同じことを定めている指示、skill が自身の性格を述べる文、変数を定義するだけで使わないコード。出力テンプレートが列を定めるなら、本文は列の定義を持たない。

7 は結合が壊れたら落ちる形にする。Phase 番号、参照先のファイル、テンプレートの列は、片側だけ変わると気付けない。壊し方の選び方は `../development/TESTING.md` § テストが空振りしていないか に従う。
