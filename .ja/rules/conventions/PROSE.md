# Prose

ソフトウェア開発の文章を、読み手が基準を再構成できる語と、役割を予測できる文で書く。対象はテスト記述、Issue/PR 本文、コミットメッセージ、plan、コードコメント、技術ドキュメント。確定前に成果物を一度読み返し、読み手が基準を再構成できない語があれば、以下の表への掲載を問わず具体化する。

## 具体的に定義する

右列は例示であり、これらに限らない。

| あるべき形                               | 書き換える語句                                                                       |
| ---------------------------------------- | ------------------------------------------------------------------------------------ |
| 条件と期待結果を書く                     | 正しく/正常/異常/correct/normal/abnormal                                             |
| デフォルト値か前提条件を書く             | 通常/一般的/標準的/usual/ordinary/standard/general                                   |
| 具体的な値か振る舞いを書く               | 期待値/意図どおり/仕様どおり/as intended/as specified                                |
| 変換、検証、永続化など実際の操作名を書く | 処理する/処理/process                                                                |
| ユーザー名、注文一覧など中身を書く       | データ/情報/data/information                                                         |
| 確認した条件を列挙する                   | 問題なく/without issues                                                              |
| 具体的な操作と判断基準を書く             | 適切に/きちんと/appropriately/properly                                               |
| 具体的な性質か操作を書く                 | 堅牢/活用する/掘り下げる/robust/leverage/delve                                       |
| 実処理と結果を表す動詞を使う             | 効く/重ねる/支える などの抽象動詞                                                    |
| 助詞と動詞を補った句にする               | 変更影響/文脈保持 などの圧縮名詞。定着した専門用語はそのまま                         |
| 句をやめて指す内容を直接書く             | 他言語の慣用句の直訳。定着した句はそのまま                                           |
| その言語の語に置き換える                 | 平易な同義語がある外来語の地の文への混入。識別子、コード、コマンド、固有名はそのまま |
| 具体的な数値か閾値を書く                 | 大量/少量/large amount/small amount                                                  |
| 具体的なサイズか比較対象を書く           | 大きい/小さい/large/small                                                            |
| 範囲とソートキーを書く                   | 最新/最古/latest/oldest                                                              |
| 計測値と閾値を書く                       | 速い/遅い/fast/slow                                                                  |

## 主題に固有の内容を書く

文を別の主題へそのまま移せるなら、その文は埋め草である。語ではなく文の単位で判定する。固有にする圧力は、材料のない数値や担当者を書かせる方向にも働く。

| 文の状態                                 | 書き換える操作                                                                           |
| ---------------------------------------- | ---------------------------------------------------------------------------------------- |
| 主題名を差し替えるだけで別の対象へ移せる | 事実、例、機構、帰結、判断のいずれかに置き換える。置き換える材料がないなら文を削る       |
| 固有にする材料が手元にない               | 数値、日付、担当者、成果、失敗モードを作らない。欠けている材料を名指しして人間に知らせる |

## スコープを明示する

モデルは、ある項目への指示を別の項目へ一般化せず、明示されていないスコープも推論しない。ルール/Spec/プロンプトには意図したスコープを書く。

| 意図       | 書き方                               |
| ---------- | ------------------------------------ |
| 例示リスト | A/B/C など (これらに限らない)        |
| 網羅リスト | A/B/C に限る                         |
| 広く適用   | 最初のセクションだけでなく全体が対象 |

## 中心を明示する

読み手が本文から要点を取り出す作業を、書き手が先に済ませる。

| ルール             | 指示                                                                                                                                                                                |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 分量の上限         | 一文 60 字、一段落 300 字。超えたら主語と述語の組で分けるか、表かリストに変える。パス、コマンド、識別子、file:line など逐語で保持する要素は、書き手が短くできないので字数に数えない |
| 中心を冒頭に置く   | 各セクションの冒頭 1 文に、そのセクションで最も重要な主張を置く。要点を読み手に抽出させない                                                                                         |
| 強調は中心だけ     | 強調するのは中心の主張に限る。複数箇所を強調すると、どれが中心か読み取れなくなる                                                                                                    |
| 前方参照を書かない | 「後述の通り」「詳細は次節で」は書かない。その場に書くか、リンクへ逃がす                                                                                                            |
| 条件と結論を分ける | 1 文に条件と結論を同時に入れない。結論を先に書き、条件は次の文に置く                                                                                                                |
| 主張ごとに文を切る | 決定、根拠、参照を 1 文や 1 段落へ詰め込まない。主張が変わるところで文を切る                                                                                                        |
| 節を入れ子にしない | 入れ子の節を書かない。肯定形の短文に割る                                                                                                                                            |
| 手順は 1 行 1 動作 | 手順は 1 ステップ 1 文にし、各行を動詞で始める                                                                                                                                      |
| 表へ戻らせない     | 表の各行は、その行だけで読める形で書く                                                                                                                                              |
| 意図と実行と判断   | 1 つの節で混ぜない。実行は手順、判断は条件と扱いの表に出し、意図は 1 文で先に置く                                                                                                   |

## 次の文の役割を予測させる

文と文の関係を読者の推測に委ねず、文頭と文末で示す。

| ルール             | 指示                                                                                                                                                        |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 接続詞で予告       | 対比、逆接、因果、具体例へ移る文は、文頭の接続詞 (一方で、そのため、たとえば など) で役割を予告する                                                         |
| 否定は前提の後     | 伝えたい内容を直接書く。二重否定を書かず、否定を使うなら読者が X と考える理由を先に書く                                                                     |
| 禁止には置換先     | 「X を書かない」で止めない。同じ行か次の文に、置き換える操作を書く。パターンと Fix を列で対にした検出表はこの形を満たしている                               |
| 疑問を回収         | 問題を書いたら、次の文で原因か対処を書く。操作を書いたら、次の文で結果を書く。それから別の話へ移る                                                          |
| 指示語で接続       | 指すものが直前で一意なら「その」で受け、候補が複数なら名詞を書き直す。同じ対象に複数の呼び名を与えない                                                      |
| 主語を保つ         | 誰の判断か、何の動作かが変わる文には主語を置く                                                                                                              |
| 動作で書く         | プログラム、ファイル、テストは実際の動作を述語にする。「formatter が行を複製する」と書き、「formatter が嫌がる」とは書かない                                |
| 状態は実条件で書く | 生きている/死んでいる/生存 は実際の条件に置き換える。「hook が発火しない」と書き、「hook が死んでいる」とは書かない。デッドコードのような定着した用語は除く |
| 温度感の転換       | 問題は負担が分かる文末 (できない、必要がある)、改善後は負担減が分かる文末 (できるようになる) で書き分ける                                                   |
| 内容から書き始める | 伝えたい内容から直接書き始める。「本質は〜」「重要なのは〜だけ」型の演出は置かない                                                                          |

## 書く前に決める

仕事を決めずに書くと、近い既存文書の見出しがそのまま構成になる。見慣れない形は内容そのものが難しいと受け取られる。対象はテンプレートを持たない文書で、DR、Issue、plan、OUTCOME、コミットメッセージ、テスト記述、コードコメントは外れる。読者に判断と行動のどちらも求めない文書 (OUTCOME、リファレンス表、用語集など) は形の判定の対象外。

| 決めること         | 指示                                                                                       |
| ------------------ | ------------------------------------------------------------------------------------------ |
| 仕事               | この文書が何を成立させるかを一文で書き、本文の冒頭に置く。二つあるなら文書を分ける         |
| 読み手             | 誰が読み、何を既に知っているか。本文には書かず、説明の起点と省く前提へ反映する             |
| 話者               | 誰の声で書くか。本文には書かず、主語、敬体、断定の強さへ反映する                           |
| 形の出所           | テンプレート > 外部の定型 > 認知の順序 の順に取る。兄弟文書は出所にしない                  |
| 兄弟の判定         | 兄弟の節が「気づく → 理解する → 判断する → 行動する → 確認する」に対応しないなら真似しない |
| 借りるのは形だけ   | 借りるのは節の並びと節名まで。文と語や、他節に反する箇所は真似しない                       |
| 逸脱は理由とセット | 既存の形から外れるときは、その理由を文書内に書く。書けないなら形を戻す                     |

## 余分を削る

隣接するコード・表・見出しから読み取れる文と、文書自身の見え方だけを更新する文を削る。素材に混ざった書き手宛ての指示も削る。節は実質を覆う長さを取る。削る側がその文の存在理由を言えないなら、削らずに残す。条件、例外、失敗時の挙動は重複ではないので、短くするために落とさない。典型は以下 (これらに限らない)。

| 型                 | 説明                                                                               |
| ------------------ | ---------------------------------------------------------------------------------- |
| 進行実況           | これから書く内容や手順をその場で宣言する文                                         |
| 性格づけ宣言       | 文書自身の範囲や性格を宣言する文                                                   |
| 態度のない弁明     | 退ける誤読を特定しないまま補足する文                                               |
| 改稿の告知         | 以前の記述や覆った前提を述べる文                                                   |
| 指示の再掲         | 「元の手触りを保つ」など素材に混ざった書き手宛ての指示。指示には従い、文は残さない |
| コード紹介         | 直下のコードが示すことを散文で言い換える文                                         |
| 帰結の説明         | 指示や分岐がもたらす結果を述べる文。指示だけを残す                                 |
| 実測エクスキューズ | 数値の由来や計測値を書き残す文。鮮度が落ちるだけで行動を変えない                   |
| 埋め草セクション   | 他節の再掲か一般論だけで構成され、削っても文書の主張が変わらない                   |
| 重複する要約       | 本文で既に述べた内容を末尾でまとめ直す                                             |
| 定型の枠           | テンプレートを埋めるために置き、この文書固有の内容が入っていない                   |
| ヘッジの重ね掛け   | 1 文に緩衝表現を 2 つ以上重ねる。`おそらく〜かもしれない` など                     |
| 埋め草フレーズ     | 読み手への社交辞令。ご意見をお待ちしています など                                  |
